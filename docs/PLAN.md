# ReemoPOS — แผนพัฒนา

ReemoPOS คือ POS แบบ SaaS ที่ให้เจ้าของคนเดียวดูแลหลายร้าน หลายสาขา และหลายประเภทธุรกิจได้ในระบบเดียว
จุดขายหลักคือ login ครั้งเดียว เห็นเงินของทุกร้าน และมีโมดูลขายส่ง B2B ที่คู่แข่งในไทยแทบไม่มี

ชื่อแบรนด์ทั้งหมดเก็บไว้ที่ `config/brand.php` ถ้าผลตรวจเครื่องหมายการค้าไม่ผ่าน เปลี่ยนที่ไฟล์นี้ไฟล์เดียว

## สิ่งที่ตกลงกันแล้ว

| เรื่อง | ข้อตกลง |
|---|---|
| รูปแบบธุรกิจ | ขาย SaaS ออนไลน์ มีทดลองฟรีและแพ็กเกจ (`plans`) |
| นิติบุคคล | รองรับทุกแบบ: บุคคลธรรมดา, บริษัท, จด VAT และไม่จด VAT โดย 1 นิติบุคคลมีได้หลายร้าน |
| แต้มสะสม | อยู่ระดับ Organization ใช้ข้ามร้านได้ และมีรายงานหักกลบระหว่างนิติบุคคล (เฟส 4) |
| Offline | หน้าขายเป็น PWA ที่ขายได้แม้เน็ตหลุด: primary key เป็น ULID, เลขบิลแยกตามเครื่อง และ sync แบบ idempotent (เฟส 3) |
| กฎสรรพากร | บิล POS ที่ปิดแล้วแก้ไม่ได้และย้อนวันที่ไม่ได้ ถ้าผิดให้ยกเลิก (void) หรือออกใบลดหนี้/ใบเพิ่มหนี้ มีรายงาน Z และหมายเลขเครื่อง ภ.พ.06 ส่วนเอกสารย้อนวันอยู่ในโมดูล B2B |
| อุปกรณ์ | Android POS (Sunmi), iPad, PC + เครื่องพิมพ์ USB/LAN/Bluetooth |
| PDPA | เก็บความยินยอมแยกตามวัตถุประสงค์, ลบหรือส่งออกข้อมูลลูกค้าได้, 2FA, ทุกการเข้าถึงของ platform admin มี log |
| Stack | Laravel 13 + Filament 5 (หลังบ้าน), Sanctum (API ของเครื่อง POS), Vue 3 PWA (หน้าขาย, เฟส 3) |

## โครงสร้าง Tenancy

```
User ──< organization_user (org_role, pin) >── Organization ── Plan
                                                 ├── LegalEntity (เลขผู้เสียภาษี, VAT)
                                                 │     └── Store (business_type, modules)
                                                 │           └── Branch (รหัสสาขาตามกฎหมาย)
                                                 │                 └── Terminal (token, เลข ภ.พ.06)
                                                 ├── Role (สิทธิ์ที่สร้างเองได้)
                                                 │     └── RoleAssignment (user + store + branch?)
                                                 └── AuditLog
```

- ทุกตารางที่เป็นข้อมูลของลูกค้ามี `organization_id` และถูกกรองด้วย global scope (`BelongsToOrganization`) ตาม `CurrentTenant`
- ถ้ายังไม่ได้เลือก tenant เช่นตอนรันจาก console หรือ platform admin scope จะไม่กรอง ดังนั้นโค้ดฝั่งลูกค้าต้องตั้ง tenant เสมอ ซึ่ง Filament และ API middleware ทำให้แล้ว

## สิทธิ์ 2 ระดับ

**ระดับ Organization** (`organization_user.org_role`)

| บทบาท | ขอบเขต |
|---|---|
| owner | ทำได้ทุกอย่าง รวมถึงแพ็กเกจ, การชำระเงิน, ลบ org และโอนความเป็นเจ้าของ |
| admin | ทำได้ทุกอย่าง ยกเว้นแพ็กเกจ/การชำระเงิน และลบ org |
| accountant | ดูรายงาน, การเงิน, ภาษี และ audit log ของทุกร้านแบบอ่านอย่างเดียว |
| member | ไม่มีสิทธิ์เอง ได้สิทธิ์จาก RoleAssignment เท่านั้น |

**ระดับ Store/Branch** (`roles` + `role_assignments`)

แต่ละ org ได้บทบาทเริ่มต้น 5 แบบ แก้ไขได้ และสร้างเพิ่มได้

| บทบาท | หน้าที่ |
|---|---|
| store_manager | ผู้จัดการร้าน |
| cashier | แคชเชียร์ |
| waiter | พนักงานเสิร์ฟ |
| kitchen | ครัว |
| stock_keeper | ดูแลสต็อก |

- รายการสิทธิ์ทั้งหมดอยู่ที่ `App\Support\Access\Permission`
- RoleAssignment ที่ `branch_id = null` หมายถึงได้สิทธิ์ทุกสาขาของร้านนั้น
- การตรวจสิทธิ์ทั้งหมดผ่าน `App\Support\Access\AccessManager`

## เฟส 2: สินค้าและสต็อก

- **แคตตาล็อกแยกตามร้าน**: สินค้า → ตัวเลือก (SKU) → หน่วยนับ (เช่น ลัง = 24 ชิ้น) → บาร์โค้ด (ระบุตัวเลือก + หน่วย) → ราคาตามช่องทาง/สาขา/จำนวนขั้นต่ำ ทุกร้านคัดลอกสินค้าไปร้านอื่นได้
- **สต็อกนับเป็นหน่วยฐาน ต่อสาขา**: `StockService` เป็นที่เดียวที่แก้สต็อก ทุกครั้งที่แก้จะล็อกแถว `stock_levels` และเขียน `stock_movements` (แก้ไขย้อนหลังไม่ได้) ต้นทุนคำนวณแบบถัวเฉลี่ยเคลื่อนที่ ล็อตตัดแบบหมดอายุก่อนออกก่อน (FEFO)
- **ต้นทุนรับเข้าจากใบสั่งซื้อ**: ร้านที่จด VAT จะตัด VAT ออกจากต้นทุน ร้านที่ไม่จด VAT จะนับ VAT เป็นต้นทุนด้วย
- **เลขที่เอกสาร** (PO/TR/SC) รันต่อเดือนต่อร้าน ผ่าน `DocumentNumber` ซึ่งล็อกแถว sequence
- **API สำหรับเครื่อง POS**: `GET /api/v1/terminal/catalog?since=` (ครั้งแรกส่งทั้งหมด ครั้งต่อไปส่งเฉพาะที่เปลี่ยน) และ `GET /barcode/{code}` (รองรับบาร์โค้ดจากเครื่องชั่ง prefix 20–29)
- **ชื่อตารางชนกับระบบเดิม**: ระบบเดิมใช้ตาราง `products` อยู่ ตารางสินค้าใหม่จึงชื่อ `catalog_products` และย้าย model ของระบบเดิมไปไว้ที่ `App\Models\Legacy\*` ในเฟส 3–4 ตาราง `orders` และ `customers` ก็จะชนแบบเดียวกัน ให้ตั้งชื่อตารางใหม่หลีกเลี่ยงไว้ด้วย

## ระบบเดิม (legacy)

- โค้ดเดิมยังรันอยู่ที่ path เดิม (`/home`, `/products` ...) เพื่อให้ร้านเดิมใช้งานต่อได้ระหว่างพัฒนา
- เข้าได้เฉพาะ user ที่มี `can_access_legacy = true` (user เดิมทุกคนตั้งค่านี้ไว้แล้ว) เพื่อกันลูกค้า SaaS เข้าไปเห็นข้อมูลเดิม
- ปิดการสมัครสมาชิกของ legacy แล้ว
- จะลบโค้ด legacy หลังเฟส 7
